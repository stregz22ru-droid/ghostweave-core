RFC-001: REPLAY METADATA SEPARATION

СТАТУС: ПРИНЯТО
ДАТА: 2026-07-20
АВТОР: АРХИТЕКТОР (ДИПБРО) / LEAD DEVELOPER (АГЕНТ C)

1. ПРОБЛЕМА

При воспроизведении (Replay) событий из GHOSTWEAVE текущая структура содержит как метаданные (подписи, хеши, временные метки, идентификаторы), так и полезную нагрузку (payload) в одном объекте. Это приводит к:

- избыточному объёму данных при передаче,
- сложности фильтрации и поиска,
- смешению служебной и бизнес-логики.

2. РЕШЕНИЕ

Разделить событие на две части:

- METADATA — служебная информация (подпись, хеш, timestamp, source, eventType, id)
- PAYLOAD — полезная нагрузка (данные, которые обрабатывает агент)

При Replay сначала восстанавливается METADATA, затем по ссылке (contentHash или id) подгружается PAYLOAD.

3. СТРУКТУРА

Event {
  metadata: {
    id: string;
    timestamp: string;
    source: string;
    eventType: string;
    signature: string;
    hash: string;
    previousHash: string;
    contentHash: string; // ссылка на payload
  },
  payload: any; // загружается отдельно
}

4. ПРЕИМУЩЕСТВА

- Уменьшение размера событий при Replay.
- Возможность кэшировать метаданные отдельно.
- Гибкость в хранении payload (S3, файловая система, внешние хранилища).
- Упрощение аудита (метаданные компактны).

5. РЕАЛИЗАЦИЯ

- В GHOSTWEAVE при записи события сохранять метаданные и payload отдельно.
- При Replay сначала запрашивать метаданные, затем по contentHash подгружать payload.
- Для малых payload (< 1 КБ) можно хранить inline (опционально).

6. ТЕСТЫ

- Проверить, что при Replay восстанавливаются все поля.
- Проверить, что payload загружается корректно.
- Проверить, что размер уменьшился.

7. ДАЛЬНЕЙШИЙ ШАГ

- Внедрить в GHOSTWEAVE Core.
- Обновить клиентские адаптеры (Пандора, ACTOR).

ЗАКЛЮЧЕНИЕ

Решение принято. Реализация начинается после утверждения.
